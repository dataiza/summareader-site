SummaReader

A reader that pulls in what you follow — feeds, articles, YouTube, Mastodon, Nostr — summarizes it, and keeps the result in step across your own devices.

  • Your library is kept on your devices. We run no server that receives it.
  • Summaries run on this device by default, once you download a model. You can point them at your own server or a cloud API instead, and then the article's text goes there. Other things also connect out — the hidden page renderer, Hugging Face, the update check, the phone's system backup, the local servers — and the privacy policy lists them all.
  • Sync is end-to-end encrypted: the server holds ciphertext against sequence numbers and cannot read any of it.

There is no server-side summarization, no server-side search, and no web reader. Those are not missing features; they follow from the first line.

What you can paste

Press + beside Your shelf and paste an address. The right thing happens:

Coming from another reader, Configuration › Advanced › Your data › Import takes an OPML file and everything in it arrives as a source.

Where summaries run

Summaries run on this device by default, but no model is downloaded on first run. The reader works with no language model at all until you download one, or set your own server or a cloud API.

This deviceGemma, as an optional download of about 2.6 GB. Nothing leaves the machine. Slower, and it costs battery.
The system modelOn iOS 26 and macOS 26, where Apple Intelligence is on. Nothing to download, and nothing leaves the device.
Your own serverAny OpenAI-compatible endpoint — Ollama, LM Studio, llama.cpp.
A cloud APIYour own key. Faster, costs money, and the article's title, description and text go to that provider.

The address and model are stored in the library; the API key goes to the system keychain, never beside your library. On Linux, if the Secret Service is unavailable or locked, it falls back to an owner-only file and says so rather than pretending otherwise.

How it works

One item, one identity

An item's id is a hash of its canonical URL, so the same article arriving from a feed, from a share and from a Mastodon link is one item listed under each. That is also what makes merging two devices a set union rather than a reconciliation problem.

Summaries are chunked, mapped and reduced

Long transcripts are split to a prefill budget using a real tokenizer, not chars / 4 — measured, that rule of thumb undercounts Slovak by about 43% and Czech by about 51%, which overflows the context and truncates the model's reply.

Retention is two-tier

The extracted text and the title picture go first, reclaiming almost all the space while metadata and summaries stay; the picture's address is kept, so opening the article later fetches it again. Items go later. Anything saved, pinned, annotated or awaiting a summary is never purged — highlights are user-authored and may exist nowhere else.

Sync is a log of encrypted entries plus content-addressed blobs

The server holds ciphertext against sequence numbers and cannot read any of it. Deletion travels as explicit tombstones; an empty server never causes local deletion, because a server can be empty for several reasons and only one of them means anything was deleted.

Two things worth naming. A page that builds its text with scripts is opened once in the system's own web engine, without showing it, and the text is read from the result. The page's scripts run then, trackers included, and the engine forgets the site after each page; the privacy policy says more. And chunk sizes are provisional until the prefill benchmark runs on real mobile hardware.

Getting it

SummaReader is in testing. Builds go out through GitHub releases (free edition, Linux and Android), Google Play, Apple's TestFlight and the App Store, and not every edition is on every channel yet. There are no downloads on this page and no waiting list to join — a waiting list is a server holding your address, which is the thing this app exists to avoid.

If you want to follow it or try it, write to development@dataiza.sk.
